# API Contract — Ergene River Water Pollution Monitoring System

This document is the API contract provided by the backend and consumed by the web/mobile/AI service.
**Rule:** If anything here is to change, this file must be updated first, then the code is written — not the other way around.
Keep the Status column (`Draft` / `Approved` / `Changed`) up to date.

---

## Common Definitions

### `parameter` — valid values
| `parameter` | Symbol |
|---|---|
| `arsenic` | As |
| `copper` | Cu |
| `iron` | Fe |
| `zinc` | Zn |
| `chromium` | Cr |
| `cadmium` | Cd |
| `lead` | Pb |
| `nickel` | Ni |
| `manganese` | Mn |


> **The unit is not fixed, it depends on `sample_type`:**
> - `groundwater` / `surface_water` → **mg/L**
> - `sediment` → **mg/kg**
> The backend must validate the `unit` field based on `sample_type` (e.g., if an mg/kg value comes with
> "surface_water", it should be rejected).
> and the backend enum is updated together.

### `sample_type` — valid values
`groundwater` · `surface_water` · `sediment`


### `source_type` — valid values
`literature` (from published articles) · `simulated` (generated by us) · `sensor` · `citizen`

### BDL (Below Detection Limit) rule
For measurements falling below the device's detection limit, `value: null` and
`below_detection_limit: true` are sent. **This does not mean zero.**
The backend DOES NOT INCLUDE these records in threshold comparisons and average calculations.

### Data sources and comparison rules

- `data/ergene-2013-measurements.json`: 108 groundwater (`groundwater`) measurements,
  18 wells x 6 metals. These records should not be merged into a single trend
  series with 2021 and 2025 river water records.
- `data/ergene-2021-measurements.json`: 9 river water (`surface_water`) measurements.
- `data/ergene-2021-risk.json`: 4 ready literature risk assessments.
- `data/ergene-2025-measurements.json`: 90 river water and sediment measurements,
  5 stations x 9 elements x 2 mediums.
- `data/ergene-2025-risk.json`: 5 ready literature risk assessments.
- 2013 groundwater, 2021/2025 river water, and sediment records are not the same physical medium
  or the same unit; the frontend must display them as separate series/filters.
- 2013 and 2021 coordinates are subject to source/assumption limits. 2025 coordinates
  are approximated from figures and marked with `coordinate_source`.

### Frontend integration rules

- The frontend does not generate/guess location, parameter, sample type, or source type values itself;
  it uses the values it receives from API responses.
- `GET /api/locations` is used for the location dropdown. The selected `location_name`
  is sent unaltered in `GET /api/risk-status` and `GET /api/risk-assessments` requests.
  `URLSearchParams` or `encodeURIComponent` is used for the query string.
- `station_no` can be null in 2013 records; the frontend should not assume a station number
  exists for these.
- `coordinates` can be null. The map should skip records without coordinates or
  display them as non-coordinate entries.
- The `GET /api/observations` response provides `location_name`, `coordinates`, `timestamp`,
  `parameter`, `value`, `unit`, `below_detection_limit`, `sample_type`, `source_type`,
  and `risk_flagged` fields. Source JSON metadata fields are not automatically added to this response.
- The `GET /api/risk-assessments` response provides ready CR/THI values, `risk_level`, and
  `source_concluded_high_risk` fields. CR is not recalculated.
- The `water_quality` field in the Observation request is currently accepted; however, it is not returned
  in the current MVP response DTO and is not stored as a separately queryable column.

### FHIR MVP boundaries

- The backend POSTs Observation and RiskAssessment to FHIR with raw JSON.
- A LOINC code is not fabricated for Observation; `code.text` is used.
- The `id` returned by the FHIR server is written to the `fhir_observation_id` or
  `fhir_risk_assessment_id` field in the respective entity. This ID does not have to be
  the same as the application's `measurement_id` or `assessment_id` value.
- Even if the FHIR integration fails, the local DB record is preserved in the MVP, and the FHIR ID can
  remain null; the frontend must accept that this field can be nullable.
- Citizen reports use the `POST /moderate-photo` endpoint for AI evaluation.



## 1. Submitting Observation (Sensor / Mock Data)
**Status:** Updated — based on the real dataset
**Endpoint:** `POST /api/observations`
**Caller:** Mock data generator script / manual test

Request:
```json
{
  "location_name": "Ergene Havzasi - Kuyu 9",
  "coordinates": { "lat": 41.271667, "lon": 27.9725 },
  "timestamp": "2013-05-15T10:00:00+03:00",
  "parameter": "chromium",
  "value": 0.1,
  "unit": "mg/L",
  "below_detection_limit": false,
  "sample_type": "groundwater",
  "source_type": "literature",
  "citation": "Arkoc, O. (2014) Bull Environ Contam Toxicol 93:429-433, Table 1"
}
```

### Additional fields
- `method` (string) — e.g. `"ICP-MS (Agilent 7700)"`
- `station_no` (integer, optional)
- `coordinates` — can now be **nullable** (some literature sources lack numerical coordinates)
- `coordinate_source` (string, optional) — e.g. `"approximated_from_figure"`, marks where
  the coordinate came from
- `water_quality` (object, optional, only for water samples) —
  `{ ph, ec_us_cm, tds_mg_l, salinity_psu, do_mg_l }`



BDL example (cadmium resulted in BDL across all wells):
```json
{
  "location_name": "Ergene Havzasi - Kuyu 9",
  "coordinates": { "lat": 41.271667, "lon": 27.9725 },
  "timestamp": "2013-05-15T10:00:00+03:00",
  "parameter": "cadmium",
  "value": null,
  "unit": "mg/L",
  "below_detection_limit": true,
  "sample_type": "groundwater",
  "source_type": "literature"
}
```

Response `201 Created`:
```json
{
  "id": "erg-obs-2026-0347",
  "fhir_observation_id": "erg-obs-2026-0347",
  "risk_flagged": true,
  "exceeded_standards": ["TS_2005", "WHO_2006"]
}
```
> `exceeded_standards`: lists which standards were exceeded. Empty array if none were exceeded,
> also empty array for BDL records (`risk_flagged: false`).

## 2. Submitting Citizen Report
**Status:** Updated
**Endpoint:** `POST /api/citizen-reports`
**Caller:** Mobile application

Request (`multipart/form-data`):
- `photo` (MultipartFile)
- `category` (String)
- `note` (String)
- `latitude` (Double)
- `longitude` (Double)
- `timestamp` (String)

Example form fields:
```text
photo=<binary file>
category=kirli_renk_degisimi
note=Suyun rengi koyu kahverengiye dönmüş, koku var.
latitude=41.1605
longitude=27.8021
timestamp=2026-08-18T14:22:00+03:00
```
Response `201 Created`:
```json
{
  "id": "cit-uuid",
  "ai_validation_status": "ONAYLANDI",
  "ai_confidence": 0.87
}
```

## 4. Updating Citizen Report Status

**Status:** Approved  
**Endpoint:** `PATCH /api/citizen-reports/{id}/status`  
**Caller:** Municipality staff

Request:

```json
{
  "status": "ONAYLANDI"
}
```

Valid target statuses:
- `ONAYLANDI`
- `TUTARSIZ`

Within the scope of the MVP, only citizen reports in `INCELEMEDE` status can be transitioned to `ONAYLANDI` or `TUTARSIZ` by municipality staff.

Response `200 OK`:

```json
{
  "id": "cit-uuid",
  "ai_validation_status": "ONAYLANDI"
}
```

Returns `404 Not Found` for an unfound report, `400 Bad Request` for an invalid status or invalid status transition.

## 4. Querying Risk Status
**Status:** Updated — location matching rule clarified
**Endpoint:** `GET /api/risk-status?location=Ergene%20Havzasi%20-%20Kuyu%209`
**Caller:** Web dashboard, mock hospital panel

> **RULE:** The `location` parameter must match the `location_name` value retrieved from
> `/api/locations` or `/api/observations` responses **exactly (case-sensitive)**.
> The frontend must not generate/guess this value itself — it must solely send back a value
> previously received from the API. For spaces and special characters,
> `URLSearchParams`/`encodeURIComponent` must be used.

Response `200 OK`:
```json
{
  "location": "Ergene Havzasi - Kuyu 9",
  "current_risk_level": "high",
  "parameter": "chromium",
  "value": 0.1,
  "unit": "mg/L",
  "threshold": 0.05,
  "standard": "WHO_2006",
  "reason": "Olculen krom degeri (0.1 mg/L), WHO (2006) icme suyu rehber degerini (0.05 mg/L) asiyor.",
  "last_updated": "2013-05-15T10:00:00+03:00"
}
```

## 5. AI Photo Validation (Internal API, Backend → AI Service)
**Status:** Updated
**Endpoint:** `POST http://ai-service:8000/moderate-photo`
**Caller:** Backend (automatically triggered upon receiving a citizen report)

Request:
```json
{
  "photo_url": "https://.../uploads/citreport-1183.jpg",
  "category": "kirli_renk_degisimi"
}
```
Response `200 OK`:
```json
{
  "tutarli": true,
  "guven_skoru": 0.87,
  "aciklama": "Fotoğrafta koyu renkli, bulanık su net görülüyor, seçilen kategoriyle tutarlı.",
  "moderation_status": "approved"
}
```
Moderation status:
- approved: The image is consistent with the category and confidence score >= 0.80.
- review: Low confidence or category cannot be validated from the image.
- inconsistent: The image is inconsistent with the category with a high confidence score.

kotu_koku and other specific categories are always routed to the review status.

## 6. Submitting Health Risk Assessment (From Literature)
**Status:** Approved
**Endpoint:** `POST /api/risk-assessments`

### Mandatory additional field
- `source_concluded_high_risk` (boolean) — the final risk judgment stated by the source in its own text
  or `basis_note` field. The backend does not calculate this value; it stores the value
  sent in the request.

> `carcinogenic_risk` values are not on a consistent scale across sources and are not
> subjected to automatic threshold comparison by the backend. `risk_level` will be
> `high` if `total_hazard_index.child > 1.0` or `total_hazard_index.adult > 1.0` or
> `source_concluded_high_risk: true`, otherwise it will be `normal`.

Request:
```json
{
  "location_name": "St 2 - koy ici, sanayiden uzak",
  "station_no": 2,
  "timestamp": "2025-05-15T10:00:00+03:00",
  "carcinogenic_risk": { "child": 1.097609, "adult": 1.015173 },
  "total_hazard_index": { "child": 3.050103, "adult": 2.58 },
  "source_concluded_high_risk": true,
  "source_type": "literature",
  "citation": "Aydin, G.B., Tas-Divrik, M., Atun, R. (2026) Int J Environ Sci Technol 23:621, Table 9"
}
```
Response `201 Created`:
```json
{ "id": "erg-2025-st2-hra", "fhir_riskassessment_id": "erg-2025-st2-hra" }
```

## Threshold Values Reference (mg/L)

Source: Arkoç (2014), Table 2 — TS (2005), WHO (2006), EPA (2013)

| Metal | TS 2005 | WHO 2006 | EPA 2013 |
|---|---|---|---|
| copper | 2 | 2 | 1.3 |
| iron | 0.2 | 0.3 | 0.3 |
| zinc | — | 3 | 5 |
| chromium | 0.05 | 0.05 | 0.1 |
| cadmium | 0.005 | 0.003 | 0.005 |
| lead | 0.01 | 0.01 | 0.015 |

> No value is defined for `zinc` in the TS standard — the backend does not include that standard
> in comparisons in this case (a null check is required).
